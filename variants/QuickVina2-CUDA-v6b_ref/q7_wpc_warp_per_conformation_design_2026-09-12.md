# Q7-WPC 设计立项书: 单 Warp 负责一个构象优化 — 2026-09-12

> 用户问题: 目前一个 threadblock 负责一个构象, 每块持有可共享只读副本。
> 能否改为**单 warp 负责一个构象**, 同块各 warp 共享只读信息、各自维护
> 可写信息? 技术上是否可行? — design-first。
> 前置: Q5.1 (9b9fc61e, tag Q5.1, binary md5 2fc85d46) 已提交为新主线。

## 〇、结论先行

**技术上可行**, 无硬性架构障碍。但收益方向与直觉相反: 这个改造**不是**
免费的吞吐提升——它用"单轨迹并行宽度减半"换"轨迹密度提升", 本质是
redocking k2(单配体时延)与 screening 吞吐之间的再平衡。建议以
**Option B(64 线程块 = 2 warp = 2 构象)** 作为 spike 首选, 并以实测
裁决。以下为完整推导。

## 一、现状资源审计(Q5.1, 64t, 1 构象/块, SHARED=12,684B)

### 1.1 shared 逐项清单(代码行号实测)

**真正跨构象只读(每配体/每受体一份)**:
| 项 | 大小 | 说明 |
|---|---|---|
| rigid_cl 静态拓扑(children_map/parent/atom_range/axis/relative_*) | 2,128B | set_update 只写 origin/orientation_q, 这些只读 |
| grids_cuda(网格元数据, 无 m_data) | ~1,442B | 每受体只读 |

小计 ≈ **3,570B**

**每构象可写(轨迹私有)**:
| 项 | 大小 |
|---|---|
| m_coords + minus_forces | 3,072B |
| rigid 动态态(origin/orientation_q) | 1,064B |
| 构象/梯度状态(tmp/candidate/best_out/x_orig/gp/g/g_orig/d/xp/lm_s/lm_y/scalar_tmp/d_norm) | ~1,744B |
| POT 导数 tmp(456×2) | 912B |
| mutate scratch(acc/counter/origin/rotation) | 1,048B |
| skip_row/q4_skip_row/epoch 等位图 | ~300B |

小计 ≈ **8,140B**; 校验: 3,570 + 8,140 + warp_e 128 + 余量 ≈ 12,684 ✓

### 1.2 关键结构性事实
1. **块内跨 warp 同步全部服务同一构象**: 64t=2 warp 协作一条轨迹,
   Q4-8 加的 3 个屏障 + Q4-12 的跨 warp 归约都是为此。
2. **判定都是构象一致的**(Armijo/‖g‖/A2/metropolis 输入为块级归约值),
   分支不发散 → warp 化后同步可安全降级。
3. Q5.1 实测 issue 18.5% —— 机器远未饱和, 宽度减半不必然等比变慢。

## 二、方案空间

### Option A: 128t 块 = 4 warp = 4 构象(同配体)
- shared = 3,570 + 4×8,140 = **36,114B/块** → 2 块/SM = **8 构象/SM**
- 寄存器: 128×128=16K/块, 64K/SM → 4 块(寄存器) → shared 界定 2 块
- 轨迹密度与 Q5.1 持平(8/SM), 无密度收益, 改造量最大 → **淘汰**

### Option B: 64t 块 = 2 warp = 2 构象(同配体) ← 推荐
- shared = 3,570 + 2×8,140 = **19,850B/块** → 5 块/SM = **10 构象/SM**
- 寄存器不约束(64×128=8K → 8 块), shared 界定 5 块
- 轨迹密度 **+25%**(10 vs 8), 且只读信息 3,570B 由 2 构象摊薄

### Option C: 32t 块 = 1 warp = 1 构象
- shared = 3,570 + 8,140 = 11,710B/块 → 8 块/SM = 8 构象/SM
- 只读信息无摊薄(每构象重复加载), 密度无收益 → **淘汰**

## 三、Option B 技术改造清单

### 3.1 shared 重构(工作量主体)
- 静态区(块级): rigid 静态拓扑 + grids_cuda —— 现布局不变。
- 私有区(warp 级): 上述 8,140B 每构象项改为 **per-warp 双份**,
  两种布局:
  - SoA(推荐): `__shared__ struct ConfState { ... } conf_state[2];`
    每项按 warp 索引 `conf_state[wid].m_coords`;
  - 或 arena + 每 warp 基址指针。
- 所有 `__shared__` 声明点(~25 处)需要迁移到两个区之一。

### 3.2 屏障降级(正确性核心)
- 构象路径上全部 `__syncthreads()` → `__syncwarp(0xffffffff)`。
- **不换的死锁/串行风险**: 两 warp 轨迹迭代数不同, 若保留
  syncthreads, warp0 会在屏障处等待 warp1 的不相关进度 → 跨轨迹
  耦合, 吞吐收益归零(不死锁但变慢)。
- 屏障点清单: kernel2 grids 装载(1)+mutate(2)+eval 链(ig/pairs/POT/
  set_update/S1 树回溯 ≈ 8)+RILC/LS(Q5.1 新增 4 + 原有 ~6) ≈ **21 处**。
- 跨 warp 不再有同步 → Q4-12 的跨 warp 归约(warp_e 树)退化为单
  warp shfl 归约(v4.5 之前的形态), 代码反而变简。
- 块级只读装载(grids/拓扑): 保留一次 syncthreads(仅 kernel 启动时)。

### 3.3 索引与启动
- 全局轨迹 id: `conf_id = blockIdx.x * 2 + warp_in_block`(原为
  `blockIdx.x`); ric/results/random_maps 的 map_index 公式
  `(step + id*search_depth) % MAX_MAP` 中的 id 换成 conf_id。
- grid_size 减半(confs/2), kernel1(MC 初始化/ric)同样按 conf_id。
- 结果写回: 每 warp 写自己的 results[conf_id] 槽位。

### 3.4 需要审计的雷区(Q4-8/Q4-12 遗产)
- Q4-12 引入的跨 warp 假设(mis 装载、gyration acc): gyration 的
  acc[128]/counter[128] 归约为单 warp 内做, 检查 stride 逻辑。
- Q5.1 的 thread0 门控: 语义变为 warp0(每构象的 lane0), 即
  `threadNumInBlock==0` → `(threadIdx.x%32==0 && threadIdx.y==warp内)`
  ——实际是 `lane==0`。set_update/RILC/to_norm/LS 增量四处照搬。
- visited 位图/skip_row: 已按构象私有处理(随私有区走)。

## 四、收益与代价的诚实推算(全部需实测)

### 4.1 得
1. **轨迹密度 +25%**(10/SM): screening 场景(多配体/多构象并发)直接
   受益; v6-batch 合并后叠加。
2. **屏障成本消失**: 21 处 syncthreads(跨 warp)→ syncwarp(同 warp,
   硬件便宜一个量级); LS 串行链上的每次等待更轻。
3. **调度粒度细化**: 块内 2 条独立轨迹, warp 调度器可在轨迹 A 的
   eval 等待期跑轨迹 B 的指令 —— 轨迹级延迟隐藏(此前只有块级)。
4. 代码简化: 跨 warp 归约树删除。

### 4.2 失
1. **单轨迹 eval 宽度减半**: pairs/原子循环 stride 32。aggregate 看
   512 线程(8 conf×64t) → 320 线程(10 conf×32t), issue 18.5% 有
   大量空转槽位, ILP 可能吸收, **但不确定**。Q4-12 实测 64t 优于
   32t 是在"块=1 构象"前提下; 本设计改变的前提可能反转该结论。
2. **redocking k2 口径风险**: k2 = 单配体 8192 构象完成时间。轨迹
   变窄 → 单轨迹变慢; 密度 +25% 只部分补偿。k2 可能 +0~30%。
   **这是 Q5.1 的核心指标, 不可退化**。
3. 改造面广(~25 shared 声明 + 21 屏障 + 索引), 回归风险高于 Q5.1。

### 4.3 预期矩阵(推算, 需 spike 实测)
| 场景 | 方向 | 幅度(推算) |
|---|---|---|
| screening 吞吐(批内多配体) | 改善 | +10~25% |
| redocking k2(单配体时延) | 恶化或持平 | +0~30% |
| LS 串行等待占比 | 下降 | 屏障开销项 |

## 五、执行计划(spike-first)

### Phase 0: 1 天 spike(裁决性实验)
- 只改最小集: 64t 块→2 构象, shared SoA 双份, 全部 syncthreads→
  syncwarp, 索引换 conf_id。不追求优雅, 探针式实现。
- 门禁: 三锚点 aff 位模式 vs Q5.1 + 2×CASF k2/rt/Top-1。
- **裁决标准**: redocking k2 不劣化 >5% 且 Top-1 在带内 → 进
  Phase 1; 否则关账(记录: 轨迹密度换宽度不划算)。
### Phase 1: 完整化(2-3 会话)
- shared 布局整理 + 屏障全量审计 + 与 v6-batch 合并的兼容设计
  (batch 的 mg[ligand_id] 维度叠在 conf_id 之上)。
### Phase 2: 认证
- 2×CASF + screening 模式基准, CERT 快照。

## 六、与在途项目的关系
- **v6-batch**: 正交且互补——batch 摊 entry-gap(W0 层), WPC 摊
  shared/屏障(SM 内)。建议 v6-batch 先行(3 会话), WPC spike 在
  batch 合并后做, 避免 conf_id 语义两次返工。
- **Q6-IR**: WPC 使 Phase A(FP16) 的 shared 减半目标更容易达成
  (私有区 8,140B 中 m_coords/forces 占 3,072B, FP16 后再省)。
- **论文**: 若 spike 证实, "轨迹密度-并行宽度再平衡"可进并行层
  章节第四层叙事(工程→内存→精度域→并行)。


## 七、补充推算: 单块单 SM + shared 拉满 100KB(Q5.1 审计数据)

> 用户问题: 一个 SM 只用一个 threadblock, shared 调到 RTX 4090 允许的
> 最大值, 尽可能多 warp 共享 3,570B 只读区 — 一 SM 支持多少构象?

### 7.1 硬件口径
- RTX 4090 (CC 8.9): shared/SM = 100KB, **per-block opt-in 上限 = 99KB
  (101,376B)** — 块只能申请到 99KB, 100KB 是 SM 侧上限。

### 7.2 算术
- 静态区 3,570B + 每构象 8,268B(可写 8,140 + warp_e 128):
  - 99KB: N = (101,376−3,570)/8,268 = **11.83 → 11 构象**(用 92.3KB)
  - 12 构象需 100.38KB: 超 99KB 达 1,410B, 超 100KB 仍差 386B — 差一点

### 7.3 关键 shave: gyration 数组寄存器化 → 13 构象
- `acc[128]+counter[128]`(1,024B/构象, mutate_conf.cuh L169-171)存在的
  唯一原因是跨线程归约 128 原子。warp 化后(32 lane)可改为**寄存器
  累加 + shfl 归约**, 数组整体消失: 每构象 8,268 → 7,244B。
- 12 构象: 3,570+12×7,244 = 90.5KB ✓
- **13 构象: 97.7KB = 95.5KB/99KB ✓**
- 14 构象: 105.0KB ✗(超 99KB 3.6KB; 再 union scalar_tmp 220B 也不够)
- **答案: 不动结构 = 11 构象; gyration 寄存器化 = 13 构象/SM**

### 7.4 与 Q5.1 的密度/占用对照(8192 构象, 128 SM)
| 布局 | 构象/SM | 线程/SM | warps/SM(占用) | 波数 |
|---|---|---|---|---|
| Q5.1(8块×64t×1构象) | 8 | 512 | 16 (33.3%) | 8.00 |
| WPC-11(1块×11warp) | 11 | 352 | 11 (22.9%) | 5.82 |
| WPC-13(1块×13warp) | 13 | 416 | 13 (27.1%) | 4.94 |

### 7.5 解读(诚实)
- 密度收益真实: 8 → 13 构象/SM(+62.5%), 波数 8 → 4.94(尾效应减半)。
- **但线程/SM 反降 19%**(512 → 416), warps/SM 降 19%(16 → 13) —
  延迟隐藏资源变少; 单轨迹宽度减半的时延代价依旧在。
- 一块/SM 还引入**单点串行化风险**: 块内 13 条轨迹共享一次 block
  调度; 若驱动把 13 warp 调度不满(寄存器 13×32×128=53,248 < 64K ✓
  可满), 无碍 — 但共享存储器带宽端口竞争加剧。
- 判定不变: 这是 redocking k2 vs screening 密度的再平衡, spike 裁决。
  WPC-13 的新增实现项 = gyration 寄存器归约(独立小改动, 也可单独
  反哺 Q5.1: 省 1,024B 后 Q5.1 的 shared 12,684 → 11,660, 距 8 块
  门槛 11,776 还富余 116B — 顺手把 S4a 时代悬置的 8 块门槛问题
  彻底关闭!)。


## 八、补充推算: 保持多 warp/构象, warp 数还能提吗?(Q5.1 审计)

> 用户问题: 保持"多 warp 协作一个构象"的架构, warp 数是否还有提升空间?

### 8.1 双墙定性
- **寄存器墙(主)**: `-maxrregcount=128`(Makefile L19, sm_89)。
  RTX 4090 寄存器堆 64K/SM → 65536/(128×32) = **16 warps/SM 硬上限**。
- **shared 墙(副)**: 8 块 × 12,684B = 101.5KB, 恰好顶满 SM 侧 100KB
  (102,400B)。两墙同时绑定 — Q5.1 的 16 warps / 8 构象是双资源
  同时饱和的解。

### 8.2 块形状重分配 = 零和
多 warp/构象下 confs/SM = 块数 B(每块 1 构象), warps/SM = B×W ≤ 16
(寄存器), B×(3,570+W×8,268) ≤ 102.4KB(shared):

| W(warp/构象) | B 块/SM | confs/SM | warps/SM | 备注 |
|---|---|---|---|---|
| 2(Q5.1) | 8 | **8** | 16 | 现状, 双墙满 |
| 4 | 4 | 4 | 16 | Q4-12 实测劣于 W=2(轨迹方差) |
| 8 | 2 | 2 | 16 | 更差 |

- 结论: **重分配零和** — warps/SM 恒 16, confs 随 W 增大反而减少。
- Q4-12 已实测 W=2 优于 W=4; v4.5b 的 block-E@128=2.9× 是独立
  energy kernel 时代的口径, 不可比。

### 8.3 寄存器墙能否移动?(三条路, 全部有实测反证)
1. `-maxrregcount` 降到 96: 寄存器扫参 CAP 160/192/255 已实测
   k2 -2% 平坦(强制更紧 → 溢出更多) — 96 会更糟(STACK 已 9.8KB)。
2. 结构性降压: Q5 ncu 结论"1.32G local_st = 分布式临时量, 无单点
   可修"(B 方向证伪)。
3. FP16 寄存器存储: E1 实测坐标 FP16 破坏搜索(能量面阶梯化)。

### 8.4 与 WPC 的关系(一个统一视角)
把 16-warp 寄存器预算想成固定货币, 每构象花 W 个 warp:
- 多 warp/构象: 每构象"贵"(W≥2)但每构象宽(64t) → 8 构象
- WPC: 每构象"便宜"(W=1)但窄(32t) → shared 允许 13 构象(§七)
- shared 在 WPC 单块下被静态区摊薄是唯一能突破 8 构象的路径 —
  但代价是轨迹宽度减半 + 占用率 33.3%→27.1%。
- **两轴互斥, 无法兼得**: 宽度(多warp)与密度(WPC)共享同一个
  寄存器堆。这就是"redocking k2 vs screening 密度"再平衡的
  硬件根源。

### 8.5 顺手可做的实事
gyration 寄存器化(-1,024B/块)让 Q5.1 shared 12,684→11,660B:
- 8 块占用 93.3KB, 从"顶满 100KB"降回安全水位(驱动/编译器余量);
- 与 8 块寄存器门槛的 908B 缺口问题(S4a 悬置)一并关闭;
- 独立小改动, 可单独作为 Q5.2 落地, 不必等 WPC spike。


## 九、Q7-BH 设计: 64 regs + n warp/构象 + 单块/SM(用户综合提案)

> 用户提案: -maxrregcount=64, n warp 负责一个构象, n×k warp 组成
> 1 Block/SM — 把"多 warp 单构象"(宽度)与"单 threadblock"(静态
> shared 摊薄)结合。**这是对 §七/§八两轴互斥困境的正确解锁**。

### 9.1 资源算术(64 regs/thread, 1 Block = 32 warps = 1024 threads)

寄存器堆 64K = 1024×64 — 精确用满, 32 warps/SM(占用 66.7%):

| n(warp/构象) | confs/块 | block shared | 判定 |
|---|---|---|---|
| 2 | 16 | 132.7KB | ✗ 超 99KB(shaved 仍 116.7KB ✗)|
| **4** | **8** | **68.1KB**(shaved 60.1KB) | **✓ 最优点** |
| 8 | 4 | 35.8KB | ✓ |
| 16 | 2 | 19.6KB | ✓ |

### 9.2 为什么这个组合成立(而 §八的 W=4 失败)

§八的多块设计中 n=4 失败的原因是寄存器墙: 128regs 时 4 confs/SM。
单块设计中 64 regs 把 warp 预算翻倍到 32, 静态 shared 只付一次:
- **密度恢复**: 8 confs/SM = Q5.1 持平
- **宽度翻倍**: 每构象 128 threads(vs 64)
- **占用翻倍**: 32 warps/SM(vs 16, 33.3%→66.7%)
- **shared 节省 31%**: 69.7KB vs 101.5KB(静态区 8 份→1 份)
- Q4-12 当时"128t 更宽但被压到 4 confs"的矛盾被此方案消解 —
  v4.5b block-E@128=2.9× 的潜力终于可在 8 confs 密度下兑现

### 9.3 核心实现难点: 同步域

一个块 32 warps 含 8 个独立构象, `__syncthreads` 会耦合无关轨迹!
必须把全部 ~21 个同步点改为**构象域屏障**:
- PTX `bar.sync id, count`(sm_89 有 16 个硬件槽, id 0 留给全局):
  8 构象各占 1 个 id, count=128 — 硬件资源刚好够(8≤15)✓
- 或 cooperative_groups::tiled_partition<128>(底层同机制)
- 每个同步点需标注所属构象域(v4.5b sync 雷审计 ×8 域, 工作量主体)

### 9.4 风险与门禁

1. **64 regs 可编译性(gating 风险, 未实测)**: 当前 128 regs 下
   STACK 9.8KB 已有残余溢出。对冲因素: 宽度翻倍 → stride 循环
   trip count 减半 → 活跃区间缩短, 编译器可能自然降压; 寄存器
   扫参 CAP 160/192/255 是放宽方向(-2% 平坦), 64 是收紧方向,
   **未测过**。便宜预判实验: 现形状直接 -maxrregcount=64 编译,
   ncu 看 STACK/local 流量 + 三锚点 k2 — 若劣化 <5% 则继续,
   爆炸则关账。
2. **1 Block/SM 的调度**: 8192 构象 ÷ (8 confs×128 SM) = 8 波(与
   Q5.1 同) — 无波数收益, 收益全部来自每构象宽度与占用率。
3. **语义**: 归约顺序变化在既接受的噪声带内; 轨迹数学不变。

### 9.5 预期(推算, 需实测)
- k2: eval 宽度翻倍且 issue 18.5% 有空转槽 → **-10~-25%** 可能;
  若 64-reg 溢出打热水线循环则 +20~30%。区间宽, 全看编译器。
- 语义门禁: 三锚点 + 2×CASF 不变。
- 工作量: 2-3 会话(屏障域重构为主体 + shared SoA + 索引)。

### 9.6 执行顺序建议
1. Q5.2 = gyration 寄存器化(独立, 立即做, 顺便服务一切后续)
2. 64-reg 预判编译(半小时, gating)
3. 通过 → Q7-BH 全量实现(本节设计); 失败 → WPC Option B(§七)
