# Q4-12 S4a 系列: S1(+960B)与 S4a-3(合并)的抵消关系技术备忘 — 2026-09-12

> 问题: "S1 的 +960B 是为什么? 为什么它和 S4a-3 合并会抵消?"
> 本备忘把这条被压缩叙述跳过的推理链完整展开, 并说明为什么 S1 不是白做。

## 一、背景: POT_deriv_update 的两份数组

`POT_deriv_update`(E 的力→梯度投影, 占 E ~43%)在 S1 前的结构:

```c
__shared__ flo position_derivative_tmp[MAX_NUM_OF_RIGID][3];  // 480B/块 (Q4-5 遗产)
__shared__ flo orientation_derivative_tmp[MAX_NUM_OF_RIGID][3]; // 480B/块

flo position_derivative[MAX_NUM_OF_RIGID][3];   // ← 每线程私有! 480B/线程
flo orientation_derivative[MAX_NUM_OF_RIGID][3];// ← 每线程私有! 480B/线程
```

- `*_tmp`: 相位 1 的**跨线程并行累加**存储(原子分步, strided 写),
  本来就是 shared(Q4-5 遗产)
- `position/orientation_derivative`: 相位 2 自底向上树走的**每线程私有**
  工作数组——由于整块执行同一条轨迹, 32/64 个线程**冗余计算完全相同
  的树**, 每线程各持一份相同结果

## 二、S1 的 +960B 到底加在哪

S1 把这两个**每线程私有数组**声明为 `__shared__`:

| | 改前 | 改后 |
|---|---|---|
| deriv 数组存储位置 | 每线程 local memory(DRAM 后备) | 每块 shared(片上) |
| 每块占用 | 960B × 32/64 份 = **30-60KB local** | 960B shared(1 份) |
| 访问延迟 | local = DRAM 级(数百 cycle) | shared ≈ 30 cycle |

**+960B 指 shared 容量增加了 2 × 480 = 960B**。它的对价是消掉:

1. **每线程 ~960B 的栈/local 占用**(STACK 9984B 的组成部分;
   Q4-9R 修掉 lm 数组后剩余溢出的主要成分)
2. **local memory 读写流量**: 每次 BFGS episode 全数组读写一遍,
   这是 Q4-9R 时代 local_op_st 1.32G sectors 的残余部分
3. **每线程冗余**: 32/64 份相同计算压缩为 1 份(thread0 执行)

(注意: S1 当时还同时引入了 thread0-only 树走——这是 shared 化的
必然伴随, 否则 64 个线程对同一 shared 数组做冗余 `+=` 会把值乘 64。)

## 三、为什么说 S1 与 S4a-3 合并"抵消"——以及为什么不完全是

S4a-3 的合并把独立的 deriv 数组删掉, 相位 2 直接在 `*_tmp` 上就地
自底向上累加(DFS 序保证子节点先于父节点被终算, 现有代码本就依赖
此序)。两个 deriv 数组随之消失 → **-912B(960B 按 4 字节对齐回收)**。

表面看: +960B(S1)与 -912B(合并)相互抵消, shared 回到 12,684B。
**但如果因此推断"S1 白做了", 就错了**——抵消的是账面, 不是价值:

1. **语义转换是前置依赖**: 合并的前提是"数组是块级单份、由单线程
   顺序消费"。S1 之前数组是 64 份线程私有副本, 根本不存在"合并到
   一份 tmp"的对象。即: 没有 S1 的语义转换, S4a-3 的 -912B 无处安放。
2. **S1 消灭的 local 流量是真实收益**(Q4-9R 实测 DRAM 写 -94%、
   local_st -65% 的大头), S4a-3 的 -912B 只是把 S1 引入的临时
   shared 占用回收掉——两步的账不能对冲来看。
3. 合并还**消除了相位 2 开头的整组拷贝**
   (`deriv[i] = tmp[i]` ×2 数组 ×38 节点), 1pxn k2 57.8→55.1ms
   (-4.6%), 3ag9 1.335→1.224(-8%)。

## 四、正确的心智模型

```
S1 前: [64 份线程私有 local 数组]  ← 60KB/块 local 流量 + DRAM 后备
S1:    [1 份 shared deriv 960B] + [1 份 shared tmp 912B]   (+960B)
S4a-3: [1 份 shared tmp 912B](就地累加, 无独立 deriv)      (-912B)
终态:  shared 净增 ≈ 0, local 流量归零, 拷贝相位删除
```

S1 的 +960B 是"语义迁移的过桥费": 先把状态从线程私有搬上块级共享
(付出 960B), 再在块级语义下消除与 tmp 的重复(回收 912B)。**直接
一步到位在技术上不可行**——在线程私有意向下, "与 tmp 合并"没有意义;
在块共享受向下, 必须先有线程0 串行树走(else 64 路并发 `+=` 会把值
放大 64 倍), 而那正是 S1 的内容。

## 六、教训(方法论)

1. **重构的中间态可以有代价, 只要终态净赚**: S1 的 +960B 是语义
   迁移的必要过桥, 评估重构时按终态记账, 不按单步。
2. **抵消 ≠ 无意义**: 判断两步是否冗余, 看的是每步改变了什么
   不变量(此处: 数组从线程私有变为块级单份), 而非资源的最终数字。
3. **先转换语义, 再消除冗余**: 直接"一步合并"在私有意向下无定义
   ——这是 design-first 把重构拆成可验证小步的原因。
